# Switchboard — Phase 1 Completion Report (Item I, Phase 1 of 5)

Branch: `batch1-expansion` (Foundation); `connections-hub` (AN-repo, same branch Item C used — not pushed, see below). Ships P1 of the spec's own 5-phase rollout (§4/§5 of `SWITCHBOARD_BUILD.md`): widget core, bootstrap/threads/messages/pins endpoints, AN dashboard embed, `sb_*` schema including `open_items`.

## What shipped

**Schema** (`20260905220000_switchboard_phase1_schema.sql`): `sb_memberships`, `sb_threads` (with `open_items JSONB`), `sb_messages`, `sb_message_renderings`, `sb_pins`, `sb_settings` (with `bubble_color`/`lang`/`voice_id` per Addendum B), and a new `client_agent_entitlements` table — see "Deviations" below for why that last one exists and isn't in the spec's own list.

**Backend** (`app/app/switchboard/`):
- `auth.py` — the AN↔Foundation auth bridge. `POST /switchboard/auth/exchange` takes AN's own Supabase Auth access token, verifies it against AN's own `/auth/v1/user` endpoint (real cryptographic verification, performed by AN's Supabase server — Foundation never needs AN's JWT secret), resolves workspace membership, and mints a short-lived (1h) Foundation-signed JWT scoped to `{user_id, workspace_id, role}`. Fails closed (503) if `SWITCHBOARD_JWT_SECRET` isn't set, same pattern as `connection_broker`'s Fernet key.
- `entitlements.py` — resolves the unlock mask from `client_agent_entitlements`; missing rows default to **locked**, not unlocked (a new agent release is grayed by default, matching §2.2's "perpetual merchandising shelf" framing).
- `composer.py` — builds the LLM call: agent's real system prompt (or a minimal honest fallback built from role/department for the 27 agents without one yet, with staged PROOF OF WORK / CONVERSATION DISCIPLINE blocks spliced in) + unresolved `open_items` injected above the last-30-message window, per `05_CONVERSATION_DISCIPLINE.md` §2's "composer always injects current open items above the recent-messages window."
- `router.py` — `POST /auth/exchange`, `GET /bootstrap`, `GET /threads/{agent}`, `POST /threads/{agent}/messages`, `POST /pins`, `GET /v1.js` (serves the widget bundle).

**Widget** (`app/app/static/switchboard/v1.js`): vanilla JS, zero runtime dependencies, Shadow DOM container (`:host{all:initial}` — zero CSS bleed by construction, not just convention). FAB with unread badge, buddy list grouped by department with lock states, a chat window that calls the real endpoints. Color language (copper=AI, cobalt=people) pulled from `demo/switchboard-demo-v11.html`'s CSS custom properties. Single script tag per §3.1: `<script src="{foundation}/switchboard/v1.js" data-tenant-key="..." data-foundation-url="..." defer>`.

**AN embed**: `AN-repo/src/components/SwitchboardEmbed.tsx` sets `window.__switchboardGetHostToken` from AN's real `supabase.auth.getSession()`, injects the script tag, rendered once from `Dashboard.tsx`. Type-checked clean (`npx tsc --noEmit`, zero errors touching either file).

## Deviations from the spec, and why

1. **FK targets**: the spec's SQL references a bare `clients(id)`. Live-schema introspection (this session, 2026-09-05) confirmed no such table exists in either `foundation` or `public` — the real client table is `foundation.client_profiles`. Every FK targets that instead.
2. **New table `client_agent_entitlements`**: not in the spec's §3.3 table list. Checked live before building: `employee_platform_subscriptions` exists but is **platform**-level (which product surfaces an agent on — automation-nation/blast-video/assistmeo), not **client**-tier gating; no `client_subscriptions`/`client_entitlements`/anything client-tier exists anywhere. §3.1 itself says "Foundation serves the full roster + the entitlement mask" — this table is the minimal real thing needed to serve an honest mask instead of either unlocking everyone (defeats the locked-agent upsell mechanic, John's Locked Decision #2) or fabricating lock state with nothing behind it. A real pricing/billing engine can become a second writer later (`source` column already distinguishes `manual` from `pricing_engine`).
3. **RLS model**: the spec's policies assume browsers hold real Supabase-issued JWTs checked via `auth.jwt() ->> 'workspace_id'`. Nothing in this codebase works that way — every table built this session (and everything before it) uses `service_role_all_X` RLS because the FastAPI backend always talks to Postgres with the service-role key. Workspace/user isolation is enforced in the FastAPI layer instead: every query in `router.py` is filtered by the verified JWT's `workspace_id`/`user_id`, never by a client-supplied parameter (Addendum C.7's literal requirement — "the parameter must not exist at all" — none of the five endpoints accept one). RLS here is the same service-role-only backstop as everywhere else, not a control that would silently do nothing.
4. **Workspace auto-provisioning**: Addendum C.3 says invites come from an owner/admin; no invite system exists yet (out of scope for P1's checklist item). To let `/auth/exchange` do anything useful today, a narrow bootstrap rule was added: a first-time verified user is auto-added as `owner` **only** on an exact match between their verified email and an existing `client_profiles.contact_email`. Checked live: most real active clients (Bakerellas, Delivered Fireworks, LUTS, Exterior Rescue WNY, Broker Broker Realty) have `contact_email = NULL` — this bootstrap path will not fire for them until that field is populated. This is a real, flagged gap, not silently worked around (see "Not done" below).
5. **Thread memory window**: last-30-messages only, no rolling summary. §3.4 asks for "last 30 messages + rolling summary" — the summary half is a scheduled-compaction feature of its own, trimmed the same way Batch 2/3's follow-on pipelines were trimmed (flagged, not dropped silently).

## VERIFY — against live Supabase + a real TestClient run, not asserted

Ran `verify_switchboard_p1.py`: seeded 2 real `client_profiles` workspaces, 3 users (2 in workspace A, 1 in workspace B), real entitlement rows, minted real Switchboard JWTs, hit the live FastAPI app through Starlette's `TestClient`.

- **Bootstrap returns full roster + correct per-workspace entitlement mask**: confirmed `rahab-reputation` unlocked / `zacchaeus-books` locked for workspace A, matching the seeded entitlement rows exactly.
- **Locked agent never fake-chats**: `POST /threads/zacchaeus-books/messages` for workspace A returned 403, not a scripted reply.
- **Cross-workspace isolation**: workspace B's bootstrap shows zero unread for an agent workspace A has an active thread with; `GET /threads/rahab-reputation` for workspace B returns an empty thread, never A's messages — confirmed even when a `?workspace_id=<A's id>` query parameter is explicitly attached to the request (silently ignored — the endpoint has no such parameter).
- **Eden isolation holds within a workspace, not just across workspaces**: a second member of workspace A (`role=member`, not owner) gets their own empty Eden thread — cannot read the owner's Eden conversation. Satisfies Addendum C.7's Eden test plus the stricter within-workspace case the base spec's §3.3 RLS note calls out ("stricter than client-level — staff don't read the owner's DMs").
- **Invalid/forged token rejected**: 401.
- **A real reply-generation call was exercised, but not confirmed successful**: the Anthropic account backing this deployment returned `Your credit balance is too low to access the Anthropic API` on both real send attempts. The failure path is genuinely verified — no crash, a graceful in-thread error message, the real exception logged — but a successful LLM-generated reply was not confirmed today. **This is an account/billing issue, not a code defect, and it affects every live agent in this deployment, not just Switchboard** — flagged directly, separate from this report.
